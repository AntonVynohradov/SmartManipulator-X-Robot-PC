    SmartManipulator-X¶

    SmartManipulator-X is a robot arm project. It combines the ROS 2 control and operator-software concepts of ROBOTIS OpenMANIPULATOR-X with the mechanical design of BCN3D Moveo. Instead of DYNAMIXEL actuators, a Microchip SmartFusion2 controller drives the stepper motors of the Moveo joints and a hobby servo on the gripper, and presents them to the ROS 2 host as virtual DYNAMIXEL devices over Protocol 2.0. The ROBOTIS host software can then talk to the arm as if it were built from DYNAMIXEL servos.

    This documentation covers the whole system: the Robot PC, the controller firmware and hardware, the shared DYNAMIXEL contract, the Operator PC, and the mechanics.

    Current status¶

    • Controller firmware: builds in two variants, the target variant (TMC5160 over SPI) and the simulation variant (simulated axes on the real board, for protocol tests). Both implement a functional subset of a virtual XW430-T333-R (PING, READ, WRITE, REG_WRITE, ACTION, SYNC_READ, SYNC_WRITE). The simulation firmware passes the automated conformance check (firmware_check.py, 49/49, including the gripper servo) when it runs as native_sim on a PC.
    • Hardware (2026-10-11): the host link (460800 bps PC ↔ PIC32, 230400 bps PIC32 ↔ SmartFusion2) works on the kit. On axis A0 (BTT TMC5160T Pro, 17HS19-2504S) SPI detection, the register mapping, telemetry, Current Limit and the ramp generator are verified, but the shaft does not turn yet: the module reads SD_MODE=1 (STEP/DIR mode) instead of the motion-controller mode, see finding 10 in Firmware interface review. Motor currents, ramps and the motor-to-axis assignment are described in Motor profiles and axis assignment.
    • Gripper servo: a virtual DYNAMIXEL device on ID 7 driven by CorePWM in the FPGA fabric. On the kit it follows Goal Position; its travel is not calibrated yet.
    • Robot PC: ROS 2 Jazzy Docker image with the selected ROBOTIS packages, and skeletons of the project packages (description, bringup, config). The upstream Jazzy sources still have to be verified against the device behavior (model numbers, registers), and the BCN3D Moveo robot model (URDF, meshes) is still to be created.
    • Open items for the whole arm: joint-to-motor mapping and gear ratios on the real arm, shoulder pairing (IDs 2 and 3), joint limits, and safety (emergency stop). The verified state versus target table tracks them.

    Guides

    Getting started¶

    This guide takes you from a fresh clone to a built firmware image and a running motor tester. The development environment page has details and troubleshooting.

    Prerequisites¶

    Where What
    Host (Windows or Linux) Git, Docker Desktop / Docker Engine with BuildKit, VS Code with the Dev Containers extension
    Host, for the GUI Python 3.9+ with Tkinter (the python.org installer on Windows; python3-tk python3-venv on Ubuntu)
    Host, for the FPGA design Microchip Libero SoC with its license, outside Docker
    Hardware M2S Hello FPGA Kit, USB Mini-B cable, and for motion: six TMC5160 modules, motors, and a 24 V supply (wiring)

    The firmware toolchain (Zephyr SDK, west, CMake, Ninja, ccache) comes from the repository Dockerfile. Do not install it on the host.

    Clone¶

    git clone <repository-url> SmartManipulator-X-Controller
cd SmartManipulator-X-Controller

    The repository has a .gitattributes file, so shell scripts keep LF line endings on Windows too. If you cloned before it was added, see Line endings.

    Open the Dev Container¶

    1. Open the folder in VS Code.
    2. Press F1 and run Dev Containers: Reopen in Container.

    The first start builds the image Dockerfile, which takes several minutes. The repository is mounted at /workspace and the compiler cache at /ccache.

    Fetch Zephyr and build¶

    Press Ctrl+Shift+B to open the Zephyr: Workspace Menu:

    1. Initialize + update runs west init -l . and west update. Do this once; it downloads Zephyr v4.5.0-rc1.
    2. Pick the firmware variant:
    3. Build simulation firmware builds into build-sim/. It needs no motors or drivers, and every axis is simulated in the firmware. Start with this one to check the board, the USB/UART link, and the protocol.
    4. Build firmware builds the target firmware into build/. It drives the six TMC5160 modules over SPI.

    The same steps from the container terminal:

    west init -l .        # first time only
west update
west build -b m2s_hello_fpga_kit/m2s010 -s apps/SmartManipulator_Controller -d build-sim -- -DFILE_SUFFIX=sim
west build -b m2s_hello_fpga_kit/m2s010 -s apps/SmartManipulator_Controller -d build

    The images are written to build-sim/zephyr/ and build/zephyr/ (zephyr.elf, zephyr.hex, zephyr.bin). The firmware variants table compares the two.

    Program the board¶

    The SmartFusion2 hardware design (MSS, clocks, fabric, pins) comes from the Libero project, and the Libero tools program it on the host. Load the Zephyr image into the configured design with your Microchip programming or debug setup. Use zephyr.elf for debugging. This repository does not yet define a scripted programming workflow.

    Test the axes with the GUI (on the host)¶

    On Windows in VS Code, outside the container, press Ctrl+Shift+B and choose:

    • Create .venv: creates .venv and installs requirements.txt. Do this once.
    • Run motor tester GUI: starts the GUI with the board.
    • Run motor tester GUI (simulator): starts it without hardware.

    From a terminal instead:

    py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe tools\dxl_test_gui\dxl_gui.py          # add --sim without hardware

    python3 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt
.venv/bin/python tools/dxl_test_gui/dxl_gui.py

    Select the kit's COM port (/dev/ttyACM0 on Linux), keep 460800 bps (or choose Auto) and PIC32 bridge (&) ticked (the kit's PIC32 forwards data only after &, see Host link), and click Connect. The tool pings IDs 1-6, the controller and the gripper servo (ID 7). With the simulation firmware, the device list shows SIM · for every axis (for example SIM · 17HS19-2504S), the axes move in the simulation, and the telemetry (velocity, current, voltage, temperature) is filled in. See the GUI guide for a complete per-axis test.

    To run the automated protocol check (49 checks with the simulation firmware; protocol-only on the target firmware):

    .\.venv\Scripts\python.exe tools\dxl_test_gui\firmware_check.py --port COM5

    Safety: the motor currents and ramps come from the motor profiles (include/motor/motor_profiles.h), the motor of each axis from include/motor/motor_axes.h. Before you drive a motor, check that the profile on its axis matches the motor that is actually connected (see Motor profiles and axis assignment), and wire the motor with VM off as shown in Motor connection.

    Dev Container¶

    1. Install Docker (with BuildKit) and the VS Code Dev Containers extension.
    2. Open the repository and run F1 → Dev Containers: Reopen in Container.

    Building¶

    # target firmware (TMC5160 over SPI)
west build -b m2s_hello_fpga_kit/m2s010 -s apps/SmartManipulator_Controller -d build
# simulation firmware (no motor hardware; prj_sim.conf + _sim overlay)
west build -b m2s_hello_fpga_kit/m2s010 -s apps/SmartManipulator_Controller -d build-sim -- -DFILE_SUFFIX=sim
# simulation firmware as a Linux executable (UART on a pseudo-terminal)
west build -b native_sim/native/64 -s apps/SmartManipulator_Controller -d build-native -- -DFILE_SUFFIX=sim

    Use a separate build directory per variant. The variants are described in Firmware variants. Run these commands from the workspace root. The root is a west workspace, and -s selects the application. Make a pristine build after changes to prj.conf, Kconfig, DeviceTree overlays, CMake files, the Zephyr version, or the toolchain:

    west build -p always -b m2s_hello_fpga_kit/m2s010 -s apps/SmartManipulator_Controller -d build

    Zephyr picks the board overlay from boards/ automatically: m2s_hello_fpga_kit_m2s010.overlay for the target, and m2s_hello_fpga_kit_m2s010_sim.overlay with FILE_SUFFIX=sim. Passing -DDTC_OVERLAY_FILE=... replaces it; use -DEXTRA_DTC_OVERLAY_FILE=... to add one.

    ccache¶

    The cache lives in .ccache/ on the host and is mounted at /ccache, so it survives container rebuilds. Use ccache --show-stats and ccache --clear, or the matching VS Code tasks. The cache is only an optimization. If a build behaves strangely, make a pristine build first.

    West and Zephyr¶

    west.yml pins Zephyr v4.5.0-rc1 and imports its modules. Run west update after changing the manifest. Keep the revision pinned; never use main. A change of the Zephyr version must be verified with a build, a pristine build, the host tests, and a test on the kit.

    Host Python environment (.venv)¶

    requirements.txt in the repository root lists the host dependencies: pyserial==3.5 for the GUI, and MkDocs, mkdocs-material, mkdocs-print-site-plugin, Playwright and pypdf for the documentation. Tkinter comes with Python and cannot be installed with pip.

py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

    # Linux (repository root); first: sudo apt install python3-tk python3-venv
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt

    On Windows, the Create .venv menu action does the same. tools/dxl_test_gui/run_gui.bat creates the environment on first use.

    Tests¶

    Test Command Where
    Firmware codec (C) gcc -std=c11 -Wall -Wextra -Werror -I include src/protocol2.c tests/protocol2_test.c -o /tmp/protocol2_test && /tmp/protocol2_test in apps/SmartManipulator_Controller Container or any gcc host
    GUI codec, bus, simulator, and firmware cross-check python -m unittest discover -s tests -v in tools/dxl_test_gui .venv or the container
    Protocol conformance of the real firmware python tools/dxl_test_gui/firmware_check.py --port <COMx or /dev/pts/N> Board with the simulation (or target) firmware; or native_sim in the container

    The cross-check compiles src/protocol2.c into a shared library. It verifies that the firmware and the Python codec produce identical packets and that the firmware parser accepts the Python packets. It is skipped when gcc is not available.

    firmware_check.py sends a fixed sequence of transactions and reports PASS or FAIL per check: - PING and broadcast PING, identity registers, and Realtime Tick; - every error code; - SYNC_READ, SYNC_WRITE, REG_WRITE, and ACTION; - CRC and stuffing robustness; - the gripper servo device, if the controller reports one (protocol, limits, ramp, SYNC_WRITE); - on the simulation firmware only: position and velocity motion and telemetry.

    It never moves motors on the target firmware unless --allow-motion is given. To test the complete firmware stack without a board, inside the container:

    west build -b native_sim/native/64 -s apps/SmartManipulator_Controller -d build-native -- -DFILE_SUFFIX=sim
build-native/zephyr/zephyr.exe &          # note the /dev/pts/N it prints
python3 tools/dxl_test_gui/firmware_check.py --port /dev/pts/N

    This needs pyserial in the container Python; the image does not include it (pip install pyserial==3.5). The motor backends have no unit tests; motor_tmc5160.c must be tested on hardware.

    • Print styling lives in docs/assets/stylesheets/print.css, and the cover page in tools/docs/cover_page.tpl.

    Code style¶

    clang-format.txt holds the formatting configuration (LLVM-based, with embedded-systems customizations). clang-format looks for a file named .clang-format, so either pass the file explicitly (clang-format --style=file:clang-format.txt) or copy it to .clang-format.

    Line endings¶

    .gitattributes makes every text file LF in the working tree, including on Windows. The exceptions are *.bat, *.cmd, and *.ps1, which use CRLF. Bash in the container fails on CRLF scripts ($'\r': command not found). If an old clone still has CRLF files, commit your work and then run:

    git rm -r --cached -q . && git reset --hard

    Debugging¶

    Debug with zephyr.elf through VS Code, Cortex-Debug, GDB, and a SmartFusion2-compatible debug probe. The probe configuration depends on the board setup and is not yet defined here. The host UART carries binary Protocol 2.0 traffic, so there is no text console. Use a debugger, or route diagnostics to the spare uart1 with an explicit DeviceTree and Kconfig change.

    Updating tool versions¶

    1. Change the ARG in the Dockerfile (and its SHA-256 for downloaded archives).
    2. Rebuild the image (docker build --no-cache ... or Rebuild Container).
    3. Build, make a pristine build, and run the host tests.
    4. Test on the M2S Hello FPGA Kit.
    5. Bump the image tag and update the version tables (this page and the zephyr-smartfusion2 skill).

    CI¶

    CI should use the same Dockerfile: build the image, run west update, build both variants (build and build-sim), and archive zephyr.elf/.hex/.bin. Run the codec tests as well. Run the native_sim build together with firmware_check.py as an end-to-end protocol test. Persist /ccache through the CI cache. A firmware-only pipeline needs no Libero and no Microchip licenses.

    Licenses and secrets¶

    Never commit or bake into images: Microchip license files, license server credentials, tokens, keys, or proprietary binaries. Keep Libero on the host.

    Firmware

    Firmware architecture¶

    The application in apps/SmartManipulator_Controller turns the SmartFusion2 Cortex-M3 into six virtual DYNAMIXEL XW430-T333-R devices. Protocol 2.0 packets from the Robot PC arrive on the host UART. They are decoded and applied to a per-axis Control Table model, then executed by a motor backend: either six TMC5160 drivers on SPI (target firmware) or a simulated axis model (simulation firmware).

    Firmware variants¶

    Target firmware Simulation firmware
    Purpose Drive the robot arm Verify the DYNAMIXEL protocol implementation on the board, without motors

    Start-up order¶

    main() runs on the Zephyr main thread. Every step must succeed before the next one starts; on the first error, main() returns that errno.

    1. motor_init() calls motor_backend_init() under the backend mutex, then creates six worker threads, each with its own message queue.
    2. The target backend checks that all tmc5160_axisN_driver and tmc5160_axisN_controller devices are ready. It returns -ENODEV otherwise, which usually means an SPI or DeviceTree problem.
    3. The simulation backend resets the six axis models.
    4. dynamixel_x430_init(&x430_config) initializes the device model. IDs 1-6 map to axes 0-5. The firmware version and position scale come from Kconfig. The configuration requires protocol type 2, a host bit rate with a Baud Rate code (230400 → 23), and unique IDs of at most 252. It also starts the gripper servo device (ID 7, pulse output off).
    5. dxl_comm_init(handle_packet, NULL) registers the UART ISR, starts dxl_protocol2_rx, and enables RX. This step comes last, so no packet can reach a model that is not ready.

    The main thread then exits. The console UART is binary, so start-up errors are not printed; debug them with a debugger.

    Lock rules

    • No code path holds two locks at once. tx_mutex and motor_backend_mutex are never nested, and the completion handler runs after the worker has released motor_backend_mutex. Keep it this way to stay deadlock-free.
    • Only the backend files may call stepper_* / stepper_ctrl_* or touch SPI or the model state. Everything else submits commands through motor_submit_async. Backends need no locks of their own.
    • The XW430 state (axes[] in dynamixel_x430.c) has no lock. It is accessed only from the dxl_protocol2_rx thread. Calling dynamixel_x430_* from another thread needs a lock first.
    • The ISR uses only k_msgq_put(..., K_NO_WAIT) and atomics.

    Motor detection¶

    DYNAMIXEL Protocol 2.0 detects devices with PING. The specification describes PING as the instruction used to check whether a device exists and to read its model number and firmware version. A device that is not present does not answer. The firmware follows this model:

    Mechanism Behavior
    Driver probe (MOTOR_OPERATION_PROBE) Target firmware: reads the TMC5160 IOIN register over SPI. The axis counts as present when VERSION is 0x30. Simulation firmware: every axis is present, except those listed in SMX_SIM_ABSENT_AXIS_MASK.
    When it runs At start-up, on every PING (unicast and broadcast), and on a READ of the controller's register 2
    Axis without a detected driver Does not answer at all, like an unplugged DYNAMIXEL: no PING reply, no status packets, skipped in SYNC_READ/SYNC_WRITE and broadcast WRITE/ACTION
    Model Information (address 2, 4 bytes, read-only) Byte 0: detected driver (0x30 TMC5160, 0xFE simulated). Byte 1: configured motor frame (14/17/23, bit 7 = gearbox). Bytes 2–3: configured rated current in 10 mA units. The motor data comes from the profile assigned in include/motor/motor_axes.h; the driver byte is measured. The GUI maps frame and current back to the motor name and warns on a mismatch.
    Controller device (ID SMX_CONTROLLER_ID, default 200) Always answers PING (model number 0x5358, same Firmware Version) and READ 0–7: model, detected-axis bit mask (register 2, re-probed on read), axis count, backend (1 = TMC5160, 2 = simulation), firmware version, ID. Writes return Access Error. Hosts use it to tell "board alive, no drivers" from "board gone". Set it to 0 to disable it.

    The TMC5160 logic is supplied from VM. Without the 24 V motor supply no driver is detected, and only the controller device answers. The SPI read of IOIN is serialized by motor_backend_mutex. The upstream driver does no SPI on its own, because no event callbacks or DIAG0 interrupts are configured.

    Mapping to the stepper axes¶

    The host sees XW430-T333-R servos; each one is a stepper motor driven open loop by a TMC5160. The registers are mapped as follows. "Motor profile" means the profile assigned in include/motor/motor_axes.h (data in motor_profiles.h).

    Register Meaning on the stepper axis
    Goal / Present Position (116 / 132) 4096 units per output revolution = full steps × 16 × NUM / DEN microsteps (3200 per motor revolution at gear 1:1). Present Position is the ramp generator counter XACTUAL, not a measurement (no encoder yet): correct as long as the motor follows every step
    Profile Velocity (112) Maximum speed of position moves, 0.229 rpm of the output. 0 = Velocity Limit. Must not exceed the Velocity Limit (Data Range Error)
    Profile Acceleration (108) Acceleration and deceleration, 214.577 rev/min². 0 = AMAX of the motor profile (a stepper cannot accelerate without limit). Larger values are cut to the TMC5160 register limit
    Velocity Limit (44, RW, Torque OFF) Per axis, default MAX_RPM of the motor profile (bench values: 120 rpm NEMA17/14, 60 rpm NEMA23) converted to the output. Range 0–1023. Limits Goal Velocity and Profile Velocity
    Current Limit (38, RW, Torque OFF) Motor run current (TMC5160 IRUN), 2.69 mA units. Default IRUN of the motor profile (about 85 % of the rated current); writes up to the rated current (Data Range Error above). The driver sets the current in 1/32 steps of 3.06 A, so the value read back is rounded down to the next step. IHOLD stays at the profile value (at most IRUN)
    Present Current (126) (CS_ACTUAL + 1) × 95.8 mA: the current setting in use (IRUN while moving, IHOLD at standstill), signed with the direction; 0 with torque off. Not a measured current
    Present Velocity / Velocity Trajectory / Position Trajectory (128 / 136 / 140) VACTUAL; ±VMAX in the direction of the move; XTARGET in position modes
    Present PWM (124) 0: no duty-cycle readout in spreadCycle mode
    Present Input Voltage (144) Nominal CONFIG_SMX_MOTOR_SUPPLY_MV (24 V): the TMC5160 does not measure VM
    Present Temperature (146) 25 °C nominal; 120 °C when DRV_STATUS reports the overtemperature warning, 150 °C at overtemperature shutdown
    Hardware Error Status (70) Bit 0 input voltage: charge pump undervoltage or a driver reset after a VM interruption. Bit 2 overheating: DRV_STATUS otpw / ot. Bit 4 electrical shock: short to ground or supply. Latched until the next Torque Enable = 1
    Moving (122) VACTUAL ≠ 0 (no standstill delay)
    Max / Min Voltage Limit (32 / 34) 40 V / 8 V, the range of the TMC5160 modules
    Drive Mode, Homing Offset (10, 20) As on a DYNAMIXEL; like Current and Velocity Limit they can only be written with Torque OFF
    Raw TMC5160 registers (1024 + 4 × register, project extension) Read-only window for bring-up: READ of exactly 4 bytes at an aligned address returns that driver register (e.g. 1024 + 4 × 0x6F = DRV_STATUS). Write-only registers read 0. Access Error on the simulation firmware. tools/dxl_test_gui/tmc_diag.py decodes the important ones (IOIN pins, CHOPCONF/MRES, DRV_STATUS, MSCNT)

    Behaviour that differs from a plain register store:

    • Torque OFF stops the ramp generator at once (VMAX 0 with the largest AMAX, under 1 ms at bench speeds) before the power stage is switched off. With the normal soft stop the counter would keep counting through the deceleration while the unpowered motor no longer follows. After Torque OFF the shaft is free: if it is turned by hand or by gravity, Present Position is wrong until the axis is referenced again.
    • Position mode (3): the counter keeps the turns made in velocity or extended position mode. Before the power stage is switched on in mode 3, the firmware moves the counter by whole output revolutions so that Present Position (without the modulo) lies in 0–4095. The shaft does not move, and a Goal Position afterwards never unwinds earlier turns.
    • Operating Mode change forgets the stored Goal Position and Goal Velocity (they belong to the old mode), so Torque ON afterwards does not start a move.
    • Driver reset (VM interrupted, the TMC5160 restarts with reset values): every backend command first reads GSTAT. After a reset the firmware writes the complete configuration again (GCONF, CHOPCONF with MRES, currents, ramp, SW_MODE, COOLCONF), reports Torque OFF and Hardware Error bit 0, forgets the goals, and refuses the move that found the reset. Present Position restarts at 0. Switch Torque ON again to continue.
    • Zero position: XACTUAL is 0 at power-up, so the pose of the arm at power-up is position 0 (2048 is not the centre unless Homing Offset says so). Place the arm in a known pose before switching on, or set Homing Offset.

    The full register list with access rules is in .agents/skills/smartfusion2/SKILL.md. Shoulder axes A1a and A1b drive the same joint. Configure them identically and command both goals back-to-back (wiring note 8).

    Configuration¶

    • prj.conf: the host UART is binary. Do not enable logging, printk, or the shell on it.
    • Host UART: DT_CHOSEN(zephyr_console), which is uart0 on this board. A BUILD_ASSERT checks that it is enabled.
    • Host link bit rate: 230400 bps, set as current-speed of uart0 in both overlays (boards/m2s_hello_fpga_kit_m2s010.overlay and ..._sim.overlay). Change it only there. include/dynamixel/host_link.h turns it into DXL_HOST_BAUDRATE, which sets the Baud Rate register (code 23 for 230400, a project code because the ROBOTIS X table has none; 46 for 460800; 2 for 115200). This is the PIC32 ↔ SmartFusion2 segment and must match the PIC32 (230400). The PC talks to the PIC32 at 460800 bps, and the PIC32 forwards data only after it has received & (the GUI and firmware_check.py send it); see Host link. The Zephyr ns16550 driver programs only the integer divisor, which at the 50 MHz MSS peripheral clock gives 223214 bps (-3.1 %). dxl_comm_init() therefore sets the MMUART fractional divisor (DLR/DMR + DFR/64, MM0.EFBR): 13 + 36/64 = 230414 bps (+0.006 %). A BUILD_ASSERT stops the build if a rate would be more than 0.5 % off. On native_sim the UART is a pseudo-terminal and the rate only sets the register value.
    • Overlay: includes include/motor/motor_axes.h. Per axis it takes irun, ihold, iholddelay, the ramp (vstart … vstop), micro-step-res and shaft (when SMX_AXISn_INVERT is 1) from the assigned motor profile. The common SMX_TMC5160_* values come from the manufacturer documents: SPI 2 MHz (the MSS SPI driver turns any request below 1.67 MHz into a 25 MHz SCK), clock 12 MHz (CLK is tied to GND, so the internal clock is used), and TCOOLTHRS 0 (the driver always enables stop on stall). After any change to the headers, rebuild pristine (west build -p). See Motor profiles and axis assignment.
    • Chopper and Moving: after stepper_enable() the backend writes the chopper bits of CHOPCONF to 0x000100C3 (TOFF 3; the driver's TOFF 15 gave a loud, low chopper frequency). Moving (register 122) is read from VACTUAL over raw SPI. DRV_STATUS.stst (used before) reports standstill only 2^20 clocks (87 ms) after the last step.
    • Kconfig SMX_MOTOR_SUPPLY_MV (target, default 24000): the value reported in Present Input Voltage.
    • Kconfig SMX_MICROSTEPS_PER_OUTPUT_REVOLUTION: 0 in the target firmware, which means "per axis from motor_axes.h" (full steps × SMX_MICROSTEPS × GEAR_NUM / GEAR_DEN; with gear 1:1 this is 3200 per motor revolution). A non-zero value overrides it for all axes. The simulation firmware uses 3200.
    • Simulation parameters: SMX_SIM_DEFAULT_SPEED (3200 µsteps/s), SMX_SIM_DEFAULT_ACCELERATION (6400 µsteps/s²), SMX_SIM_HOLD_CURRENT_MA, and SMX_SIM_ACCEL_CURRENT_MA shape the simulated motion and current.

    Known gaps¶

    • Target firmware: host link, TMC5160 detection, register mapping, telemetry and the ramp generator verified on axis A0 (2026-10-11). The shaft does not turn yet, because the module runs in STEP/DIR mode (SD_MODE=1, finding 10 in TMC5160 driver modules). Gear ratios are not entered (scale is 1:1 to the motor shaft). The simulation firmware passes firmware_check.py (49/49 checks on native_sim, including the gripper servo).
    • No encoders yet: Present Position is the commanded position (XACTUAL). A stall, a too high speed or acceleration for the load, or turning the shaft with torque off is not detected.
    • No homing or reference at boot. The wiring concept expects a hand-placed start pose and XACTUAL = 0 at power-up; check this when the axes are brought up.
    • The gripper servo (CorePWM at 0x5000_0000) follows Goal Position on the kit, but the travel of 90° for 1000–2000 µs is a nominal value and is not calibrated yet.
    • GPIO LEDs, uart1, and I²C are not used yet.
    • Health counters are not exported; there is no diagnostics channel.
    • Bulk Read/Write, Fast Sync Read, Reboot, Factory Reset, Clear, and Backup are not implemented.

    Connecting¶

    1. Connect the kit's USB Mini-B to the PC. The port shows up as COMx (Windows) or /dev/ttyACM0 (Linux).
    2. Pick the port and keep Baud 460800, the rate between the PC and the kit's PIC32 (the PIC32 talks to the firmware at 230400). Keep PIC32 bridge (&) ticked: the PIC32 passes data to the SmartFusion2 only after it has received &, which the tool sends after opening the port and after every rate change (see Host link). Auto tries 460800, 230400, 115200, 57600, 1000000, 2000000, and 9600 bps and keeps the first rate at which a device answers a broadcast PING. If you pick another rate while connected, the tool switches the open port and detects the motors again. The connection label shows the rate in use. Timeout is the time the tool waits for each status packet (default 150 ms).
    3. Click Connect. The tool runs Detect motors: it pings IDs 1-6, the controller (ID 200) and the gripper servo (ID 7), and lists the axes with their driver and motor (see below).

    Scan (PING) searches any ID range. Broadcast PING asks every device to answer at once.

    Testing one stepper axis¶

    Before you drive a motor, check that the device list shows the right motor for the axis (no ⚠ config warning) and follow the bring-up checklist. Detect motors works without motor current: it only needs VM on the module (the TMC5160 logic is powered from VM).

    1. Select the motor in the device list. The tool reads its configuration.
    2. Section 2, Configuration:
    3. Operating mode: Position (3), Extended position (4), or Velocity (1). Click Apply mode. The mode can change only with torque off; the tool offers to switch torque off first.
    4. Drive mode: Reverse (bit 0) inverts the direction. Torque on by goal (bit 3) enables torque automatically on a new goal.
    5. Profile vel / acc, for example 100 / 20, then Write profile. 0 means the motor defaults: speed = Velocity Limit (address 44), acceleration from the motor profile. Profile velocity above the Velocity Limit returns Data Range Error.
    6. Homing offset shifts the zero (units of 0.088°).
    7. Section 1, Torque: click the button to switch torque ON (green) or OFF. Below the present position, the telemetry line shows velocity (rpm), current (mA), PWM (%), supply voltage, temperature, and the position and velocity trajectory. On the target firmware the current is the TMC5160 current setting in use, voltage and temperature are nominal values, and PWM is 0.
    8. Section 3, Position control: use the slider (0–4095 = 0–360° in mode 3, ±4 turns in mode 4) or type a goal, then Move to goal. You can also use the 0°/90°/180°/270° presets or jog with − / + by the chosen step.
    9. Section 4, Velocity control (mode 1): set a speed within ± the axis' Velocity Limit (× 0.229 rpm; the slider follows it), then Start / Stop.
    10. Section 5, Automatic test: enter positions A and B, cycles, dwell, and a time limit, then Start test. The tool enables torque, moves A↔B, waits for Moving = 0, and reports each move's time and the final position error. Abort stops after the current step.
    11. Section 6, All axes: Torque ON/OFF for all, all axes to the current goal with SYNC_WRITE (the firmware runs them one after another), and an LED test.

    Every action is listed under Last operations: green for success, red for an error, with a hint. For example, Access Error on position means the axis has no position scale or the operating mode is wrong.

    Testing the gripper servo¶

    The gripper servo (MG996R on CorePWM) is a separate virtual DYNAMIXEL device, ID 7 by default. It has its own Gripper tab, not a row in the device list.

    Detection. Detect motors asks the controller (ID 200) for the servo ID (controller register 5) and then pings that ID. The Board line then ends with gripper ID 7. If register 5 is 0, the firmware was built without CONFIG_SMX_SERVO, and the tab shows Gripper servo: not detected with all controls disabled. Without a controller answer, the tool tries the default ID 7.

    Header. The title shows the ID, the model (SMX gripper servo, model number 0x5356) and the firmware variant. The line below shows the output (CorePWM on the target firmware, simulated on the simulation firmware), the pulse range and travel, for example 1000–2000 µs = 0–90° (0–1024 units), and the position limits in use.

    Section Controls Registers
    1. Torque and state Torque OFF → enable / Torque ON → disable. Torque ON starts the 50 Hz pulses, Torque OFF stops them (the servo goes limp). Live values: Position, Goal, Pulse (µs, off with torque off) and Moving. Torque Enable (64), Goal Position (116), Present Position (132), Moving (122)
    2. Position Slider and Goal [°] (Enter = Move), with the matching units and pulse width next to it. Move writes the goal. Min limit, Center and Max limit move to the position limits or their middle. Goal Position (116)
    3. Configuration Profile velocity (0 = no ramp, the servo moves at its own full speed; each unit is 0.229 rpm, so 50 ≈ 69 °/s) and Write velocity. Position limits [°] and Write limits (Torque OFF only). Read configuration from servo loads velocity, limits, goal and torque into the tab. Profile Velocity (112), Max/Min Position Limit (48/52)

    The units are the axis units, 0.088° each (4096 = 360°); the servo travel 0–90° is 0–1024.

    Steps:

    1. Open the Gripper tab. Detect motors has already read the servo configuration into it. While the tab is open, the live readout polls the servo instead of the selected axis.
    2. Set Profile velocity, for example 50, and click Write velocity.
    3. Click Torque OFF → enable. The first time after power-up the servo moves to the start position (45°) at full speed, because its real position is not known.
    4. Enter a goal in degrees, drag the slider, or use Min limit, Center, Max limit, then click Move. The firmware ramps the pulse in 20 ms steps; Moving shows YES until the ramp ends.
    5. Restrict the travel to what the gripper can do: switch torque off, enter the limits in section 3 and click Write limits. The slider then covers only the new range.

    Rules and messages:

    • A goal outside the position limits is refused in the GUI with a hint; the firmware would answer Data Range Error.
    • A goal written with torque off is only stored (the log says so); the servo moves to it when torque is switched on.
    • Position limits written with torque on return Access Error.
    • STOP (Esc) also switches the servo torque off; on closing, the tool offers to switch torque off on all motors and the gripper.
    • Position is the commanded ramp position, not a measurement: the MG996R has no feedback. Check the real position by eye.

    Hello FPGA Kit wiring¶

    This page covers stage 1: SPI-only direct wiring of the M2S Hello FPGA Kit (SmartFusion2 M2S010-VF256) to six TMC5160 modules, the gripper servo, and the power supply.

    Source and status: Robot Arm Demonstrator: Direct Wiring Hello FPGA Kit → 6× TMC5160 (Stage 1, SPI only), draft Rev. D, 2026-10-07, bavariamatic. It is for review and not released, and it supersedes Rev. C (which had home switches). The original is in Wiring_RevD_DirectWiring_EN.pdf. Pin source: Hello FPGA schematics Rev. 1, p. 11.     Manufacturer documents (in datasheets/): TMC5160A datasheet Rev. 1.18, Hello FPGA Kit schematics Rev. 1, BTT TMC5160T Pro pinout (module in use), and the reference module BTT TMC5160 V1.0 schematic and manual.

    Verified on hardware (2026-10-10/11): host link (PIC32 ↔ SmartFusion2 at 230400 bps, see Host link); SCK, MOSI, MISO, CS0, 3V3 and GND to one TMC5160T Pro (axis A0 detected, registers and ramp generator work); the servo signal on J8-4 (the servo follows Goal Position). The A0 shaft does not turn yet because the module runs in STEP/DIR mode (finding 10 in TMC5160 driver modules). CS1–CS5 and the other motors are not tested yet.

    Gripper servo: connection, supply, signal level and bring-up are on Gripper servo (MG996R).

    The module pinout, the motor connection, the check against the manufacturer documents, and the firmware review are on TMC5160 driver modules.

    Concept¶

    • Each TMC5160 runs in motion-controller mode (SD_MODE=0, SPI_MODE=1). The ramps run inside the driver. The BTT TMC5160T Pro on A0 currently reads SD_MODE=1 and must be switched (finding 10 in TMC5160 driver modules). The kit drives only SPI plus six chip selects; it provides no STEP/DIR, EN, or DIAG signals.
    • No limit switches in stage 1, because the mechanics have none. As on the original Moveo, positioning is open-loop:
    • With the power off, move the arm by hand to the defined start pose.
    • At power-up, every TMC5160 starts with XACTUAL = 0 (reset value), so the start pose is position 0. The firmware does not home.
    • The joint ranges are enforced as software limits (firmware or ros2_control).
    • Host link: USB Mini-B → MCP2221A → PIC32 → SmartFusion2 MMUART_0. The link carries DYNAMIXEL Protocol 2.0 and appears on the Robot PC as /dev/ttyACM0. PC side 460800 bps, firmware side 230400 bps; the PIC32 passes data only after the host has sent &. See Host link.

    Host link (USB → PIC32 → SmartFusion2)¶

    The PC does not talk to the SmartFusion2 directly. The kit's USB Mini-B port leads to an MCP2221A USB-UART bridge, then to a PIC32, and only the PIC32 is wired to MMUART_0 of the SmartFusion2. The two UART segments run at different bit rates; the PIC32 converts between them.

    Segment Bit rate Where it is set
    PC ↔ MCP2221A ↔ PIC32 (UART2) 460800 bps Serial port on the PC: GUI Baud box (default 460800), --baud of dxl_gui.py and firmware_check.py
    PIC32 (UART4) ↔ SmartFusion2 MMUART_0 230400 bps Firmware: current-speed of uart0 in both board overlays; the PIC32 firmware uses the same rate on its side

    The PIC32 forwards nothing until it has received the character & (0x26). After opening the port, the host therefore:

    1. opens the port at 460800 bps (8N1, no flow control),
    2. sends &, which switches the PIC32 to UART pass-through,
    3. waits about 100 ms and discards any bytes received so far,
    4. sends DYNAMIXEL Protocol 2.0 frames (FF FF FD 00 …) in both directions.

    The GUI and firmware_check.py do this automatically (checkbox PIC32 bridge (&), on by default; --no-pic32-bridge turns it off). They send & again after every rate change and reconnect. That is harmless: the firmware's parser drops any byte until it sees the FF FF FD header. A ROS 2 driver or any other host program on the Robot PC must send & once after opening the port in the same way.

    The PIC32 holds back a % (0x25) that ends a packet until the next byte arrives (measured on the kit, 2026-10-11: only this value, only towards the SmartFusion2, % inside a packet passes normally). A request whose CRC ends with 0x25 (for example READ 120/4, Realtime Tick + Moving, which the GUI polls) reached the firmware only together with the next request, so every reply arrived one transaction late. The host therefore sends one 0x00 byte after any packet that ends with 0x25; the firmware's parser drops it. DxlBus in tools/dxl_test_gui/dxl/bus.py does this, and also ignores a status packet whose data length does not match the request (a late reply). Any other host program must do the same.

    Consequences:

    • The Baud Rate register (address 8) of the virtual servos reports code 23 = 230400 bps, the firmware side. It does not show the 460800 of the PC port.
    • Changing the PC rate does not change the firmware rate, and the reverse. current-speed in the overlays must stay at the rate the PIC32 uses towards the SmartFusion2 (230400).
    • Without the PIC32 (firmware running as native_sim, or a USB-UART cable straight to the firmware UART), untick PIC32 bridge (&). On a cable, use 230400 bps; on the native_sim pseudo-terminal the rate does not matter.

    Motor connection order¶

    Connect the motors in this order. Each motor goes to its own TMC5160 module, and each module's CSN goes to the chip select in the same row. Swapping two motors gives them the wrong current and ramp, and swapping two CS lines moves the motor to another DYNAMIXEL ID.

    No. Module CS (kit pin) Joint Motor Rated current DYNAMIXEL ID → firmware axis
    1 A0 CS0 (J7-3) J1 base NEMA17 17HS19-2504S 2.5 A ID 1 → axis 0
    2 A1a CS1 (J7-1) J2 shoulder (a) NEMA23 23HS2430 3.0 A ID 2 → axis 1
    3 A1b CS2 (J8-8) J2 shoulder (b) NEMA23 23HS2430 3.0 A, shaft=1 ID 3 → axis 2
    4 A2 CS3 (J8-7) J3 elbow NEMA17 17HS19-1684S-PG5 (gearbox 5.18:1) 1.68 A ID 4 → axis 3

    • The J3 elbow motor has a built-in planetary gearbox (5.18:1, at most 2 N·m at the output). motor_axes.h sets the gear ratio 57/11 on axis 3, so the position of ID 4 refers to the gearbox output shaft, not the motor shaft.

    Safety rules¶

    1. Send only 3.3 V signals to the kit. Leave J9-5 (5 V) and J9-3 (RESET) unconnected. Do not power the servo from the kit, and do not pull the servo signal up to its supply.
    2. Never route VM or motor phases over a breadboard or Dupont wires. Never plug or unplug a motor while the power is on.
    3. SPI runs in mode 3 at no more than 2 MHz (Dupont wires). SDO is high-Z while CSN is high, so the six modules can share MISO.
    4. Configure the shoulder modules A1a and A1b identically, and write their target positions back-to-back.
    5. Do not enable the TMC5160 power stages until the firmware parameters are verified (next section).
    6. Switch on the 24 V motor supply before the kit. The TMC5160 logic runs from VM; if VM comes later or drops, the chips lose their configuration. The firmware detects this (GSTAT.reset) before the next command, writes the configuration again and switches torque off; the position restarts at 0. Place the arm in the start pose again before you switch torque on.

    The module in use: BIGTREETECH TMC5160T Pro¶

    The modules fitted are the BTT TMC5160T Pro (silkscreen "TMC5160T pro"): TMC5160 with external MOSFETs, RSENSE 0.075 Ω, 3.1 A RMS / 4.4 A peak, VM 8–56 V.     Motor current settings¶

    With GLOBALSCALER = 0 (full scale, the reset value) and RSENSE = 0.075 Ω:

    IRMS = (CS + 1) / 32 × 0.325 V / 0.075 Ω / √2 = (CS + 1) × 0.0958 A

    These values are set in the motor profiles (motor_profiles.h):

    Axis Motor profile Rated IRUN IHOLD
    A0 J1 base M17HS19_2504S 2.5 A 21 → 2.11 A 12 → 1.25 A
    A1a, A1b J2 shoulder M23HS2430 3.0 A 26 → 2.59 A 15 → 1.53 A
    A2 J3 elbow M17HS19_1684S_PG5 1.68 A 14 → 1.44 A 8 → 0.86 A
    A3 J4 forearm roll M17HS13_0404S1 0.4 A 3 → 0.38 A 1 → 0.19 A
    A4 J5 wrist M14HS20_1504S 1.5 A 12 → 1.24 A 7 → 0.77 A

    IRUN is about 85 % of the rated current, IHOLD about 50 %. The 0.4 A 17HS13-0404S1 is the exception: the nearest steps are CS 2 (0.29 A, 72 %) and CS 3 (0.38 A, 96 %), and the profile uses CS 3. With such small CS values the current resolution is coarse (the datasheet recommends CS ≥ 16); a lower GLOBALSCALER on that module would fix it but is not implemented. Raise IRUN only if an axis loses steps and the motor stays below about 80 °C.

    Motor profiles and axis assignment¶

    The motor data lives in two headers in apps/SmartManipulator_Controller/include/motor/:

    • motor_profiles.h: one block of MOTOR_<KEY>_<FIELD> macros per motor type: name, NEMA frame, rated current, holding torque, full steps, MAX_RPM (default Velocity Limit, a bench value: 120 rpm for NEMA17/14, 60 rpm for NEMA23), IRUN/IHOLD/IHOLDDELAY and the six-point ramp (VSTART, A1, V1, AMAX, VMAX, DMAX, D1, VSTOP).
    • motor_axes.h: which profile drives which axis (SMX_AXISn_MOTOR, n = 0…5 = DYNAMIXEL ID 1…6), direction (SMX_AXISn_INVERT, adds shaft;) and the gear ratio (SMX_AXISn_GEAR_NUM / _DEN), plus the common microstep setting (SMX_MICROSTEPS = 16).

    The board overlay includes motor_axes.h and takes every per-axis property from it; main.c computes the position scale (full steps × microsteps × NUM / DEN) and reports the frame and rated current in Model Information. The GUI reads the same headers, so Detect motors shows the motor name and warns when a module reports a different motor than the project expects.

    To move a motor to another joint, change SMX_AXISn_MOTOR and rebuild with west build -p (pristine, because the overlay changes). To add a motor type, copy a profile block and keep the macro format (#define MOTOR_KEY_FIELD value): the GUI parses it.

    Ramp units with the 12 MHz internal clock and 16 microsteps (3200 µsteps per motor revolution):

    Register Unit 1 rev/s or 1 rev/s²
    VSTART, V1, VMAX, VSTOP 0.715 µsteps/s 4474
    A1, AMAX, DMAX, D1 65.5 µsteps/s² 49

    The profiles use VMAX 4474 (1 rev/s) and AMAX 98 (2 rev/s²) for the NEMA17/14 motors and VMAX 2237, AMAX 49 for the NEMA23 shoulder. V1 = 0 disables the A1/D1 phase; D1 must still be ≥ 1, and VSTOP must be ≥ VSTART.

    Firmware interface review¶

    Scope: boards/m2s_hello_fpga_kit_m2s010.overlay, src/motor_tmc5160.c, and the Zephyr drivers they use (adi,tmc51xx, microchip,mpfs-spi). The code was analysed first; the SPI path and detection were then confirmed on the hardware (2026-10-10), and the register mapping and ramp generator on axis A0 (2026-10-11). The motor has not turned yet (finding 10).

    What is correct¶

    • Datagrams: 40 bits, MSB first, address byte with bit 7 = write. A read sends the address twice and takes the data from the second reply, as the datasheet requires (the first reply carries the previous request's data).
    • SPI mode 3: the driver and motor_tmc5160.c request CPOL | CPHA; the MSS SPI driver maps them to SPO/SPH.
    • Chip select: each spi_transceive is one 5-byte packet with hardware slave select SS0–SS5 (reg = <0>…<5>); SS is released after the packet, so the TMC5160 latches each datagram on the rising CSN edge.
    • Detection: tmc_read_version() reads IOIN and checks VERSION (bits 31…24) = 0x30, the value for the TMC5160 and TMC5160A.
    • Power-on safety: CHOPCONF.TOFF = 0 after reset, so with EN tied to GND the bridges stay off until Torque ON calls stepper_enable().
    • Ramp limits: VSTOP (20 in every profile) ≥ VSTART (10). Profile Acceleration 0 selects the profile's AMAX, so D1 is never 0 in positioning mode; VMAX and AMAX are cut to their register limits before they are written.

    Findings¶

    # Severity Finding Fix Status
    1 Critical SPI clock. The MSS SPI driver searches CLK_GEN only from 1 to 15, so it cannot reach rates below PCLK/30 = 1.67 MHz. For the old overlay value of 1 MHz it kept CLK_GEN = 0, and the bus ran at 50 MHz / 2 = 25 MHz (TMC5160 limit: 4 MHz). Set spi-max-frequency = <2000000>: CLK_GEN = 13, SCK = 50 MHz / 28 = 1.79 MHz. Any value from 1.67 to 4 MHz works; never below 1.67 MHz. Fixed, verified on hardware
    2 Critical Clock frequency. The overlay had 16 MHz; with CLK on GND the chip runs on its internal 12 MHz. Every speed and acceleration conversion is about 33 % off. clock-frequency = <12000000>. Fixed in overlay
    3 Critical Stop on stall is always on. The pinned driver writes SW_MODE.sg_stop = 1 at init and re-enables it from a work item, whatever activate-stallguard2 says. Above the TCOOLTHRS speed (old demo value 100, about 140 rpm motor speed) an untuned StallGuard2 can stop the motor, and the axis stays stopped until sg_stop is cleared. The firmware never clears it. Set tcoolthrs = <0> (disables stop on stall and CoolStep), or clear SW_MODE in motor_tmc5160.c after init. Fixed in overlay
    4 High Motor power switched on after the kit. TMC5160 logic runs from VM. If VM comes later, or drops, the chip restarts with reset values: the overlay settings (MRES, currents, ramp, GCONF, SW_MODE) are lost. A PING re-detects the driver, but nothing is configured again. motor_tmc5160.c reads GSTAT before every command; after GSTAT.reset it writes the configuration again, reports Torque OFF and Hardware Error bit 0 (input voltage), and refuses the pending move. The position restarts at 0. Fixed in motor_tmc5160.c (tmc_check_reset())
    5 High Currents were demo values (IRUN 2, IHOLD 1). Per-axis values from the motor profiles (table above). Fixed (motor_profiles.h)
    6 High Shoulder direction. The wiring requires shaft=1 on A1b; the overlay does not set shaft on tmc5160_axis2. Set SMX_AXIS2_INVERT to 1 in motor_axes.h after the mechanics confirm the motors face each other. Open
    7 Medium Chopper off time. stepper_enable() sets CHOPCONF bits 3…0 to 1111b (TOFF = 15). That works, but gives a low chopper frequency (audible noise, more ripple); the datasheet example uses TOFF = 3. After enable, write CHOPCONF = 0x000100C3 with the axis' MRES bits (TOFF = 3, HSTRT = 4, HEND = 1, TBL = 2), or patch the driver. Fixed in motor_tmc5160.c (tmc_enable())
    8 Medium MSS SPI driver. mss_spi_disable_ints() inverts its mask and clears every CONTROL bit except the interrupt enables after each transfer; the next transfer rewrites them. The SCK idle level between transactions is therefore not guaranteed (it may be low instead of high). The unused speed variable is the source of the known build warning. Works because CSN is high between packets. Confirm SCK/CSN timing with a logic analyser during bring-up; report upstream. Open
    9 Low tmc_read_version() bypasses the driver's register lock. At boot the driver's StallGuard work item can read the same chip between the two datagrams of a probe. Effect: one wrong probe at boot at most. Probe again after init, or read through the driver. Open
    10 Critical Module in STEP/DIR mode. On axis A0 IOIN = 0x30000040: SD_MODE=1. With SD_MODE high the TMC5160 takes its steps from the STEP/DIR pins (tied to GND here), not from the internal ramp generator. Measured during a move: XACTUAL and VACTUAL change, but the microstep counter MSCNT stays constant, DRV_STATUS.stst = 1 and CS_ACTUAL = IHOLD. The shaft only holds; Present Position changes without motion. Pull SD_MODE low: on the BTT TMC5160 V1.0 open solder jumper W1 (SD) and keep W2 (SPI) closed; on the T Pro find the equivalent SD/SPI selection (not documented in the sources here). Check with tools/dxl_test_gui/tmc_diag.py: it must report SD_MODE=0, and MSCNT must change during --move. Open (hardware)

    Findings 1–3 are fixed in the board overlay (SMX_TMC5160_SPI_HZ 2 MHz, SMX_TMC5160_CLOCK_HZ 12 MHz, SMX_TMC5160_TCOOLTHRS 0). Finding 1 was the cause of the failed first detection: with the old 1 MHz setting the bus ran at 25 MHz.

    Signal level¶

    The kit I/O level is 3.3 V (IOREF = 3P3V); its pins must never see more than 3.3 V. The servo only receives the signal, so no voltage flows back into N7. Most MG996R servos switch reliably at 3.3 V, but the datasheet does not specify the input threshold.

    • If the servo jitters or ignores the pulses although the oscilloscope shows a clean 50 Hz signal at J8-4, add a one-way level shifter, for example a 74AHCT125 powered from 5 V (input 3.3 V compatible, output 5 V).
    • Do not use a resistor pull-up to 6 V on the signal line: it would drive more than 3.3 V into N7.

    Bring-up¶

    Run these steps in order. Mount the servo without the horn or with the gripper open, so a wrong pulse cannot crush anything.

    1. Firmware: flash the target firmware. In the GUI, Detect motors shows gripper ID 7 in the board line; the Gripper tab shows Output: CorePWM.
    2. Signal without the servo: connect only an oscilloscope to J8-4 and GND. With Torque OFF the line stays low. Torque ON in the Gripper tab: 50 Hz, pulse 1500 µs (start position 45°). Move to the limits: 1000 µs and 2000 µs. The Pulse field in the GUI shows the same values.
    3. Supply: with the servo unplugged, set the DC/DC output to 6 V and check the common ground (kit GND to the PSU minus).
    4. Servo: switch the 24 V PSU and the DC/DC off, plug the servo in (brown −, red +, orange signal), switch on, then Torque ON. The servo moves to the middle position at full speed.
    5. Slow test: set Profile velocity to 20–50 (27–69 °/s) and move in small steps. Watch the servo supply voltage during moves.
    6. Limits: find the open and closed gripper positions (see Calibration), enter them as Position limits with Torque OFF, and click Write limits. Repeat after every reset: the limits are not stored.

    Calibration¶

    The firmware cannot measure the servo position. Find the gripper's end positions by hand:

    1. Profile velocity about 30, Torque ON.
    2. Move in steps of 1–2° towards closed until the jaws just touch, then back off by 2–3°. Note the angle. Do not hold the servo against a stop: it then draws up to the stall current of 2.5 A and heats up.
    3. Do the same towards open.
    4. Enter both values as Position limits. For a permanent default, change SMX_SERVO_TRAVEL_DEG, SMX_SERVO_PULSE_MIN_US / _MAX_US or SMX_SERVO_INITIAL_DEG in Kconfig and rebuild.

    If the measured rotation for 1000–2000 µs differs from 90°, set SMX_SERVO_TRAVEL_DEG to the measured angle so the GUI shows true degrees.

    Safety¶

    1. Never power the servo from the kit (J9-5 5 V, J9-4 3V3) or over the breadboard.
    2. Only 3.3 V signals on J8-4. No pull-up to the servo supply.
    3. Plug or unplug the servo only with the DC/DC output off.
    4. Torque OFF (or STOP, key Esc, in the GUI) removes the pulses: the servo is limp and the gripper may open under load.
    5. The servo position after power-up is unknown. The first Torque ON moves at full speed to the start position: keep hands out of the gripper.

    System context

    System Architecture¶

    Project objective¶

    The target is to use the ROS 2 control and operator-software concepts of ROBOTIS OpenMANIPULATOR-X with the mechanical design of BCN3D Moveo. A Microchip SmartFusion2 (M2S Hello FPGA Kit) replaces the DYNAMIXEL actuators: it drives stepper motors on the Moveo mechanism and a hobby servo on the gripper, and presents them to the host as virtual DYNAMIXEL devices.

    These sources have different roles. OpenMANIPULATOR-X is the reference for the ROS/DYNAMIXEL software stack; BCN3D Moveo is the mechanical reference. The OpenMANIPULATOR-X robot geometry, joints, actuator assumptions, and hardware configuration must not be copied as if they described Moveo.

    System context¶

    The SmartFusion2 is a motor controller implementing device behavior; it is not merely a USB-to-DYNAMIXEL converter. Details of each link:

    Link Implementation Reference
    Robot PC ↔ kit USB Mini-B → MCP2221A (CDC ACM) → PIC32 → MMUART_0. PC side 460800 bps, firmware side 230400 bps; the PIC32 forwards only after the host has sent & Host link
    Firmware ↔ stepper drivers MSS SPI_0, routed through the fabric to the Arduino header, six chip selects; TMC5160 in motion-controller mode (no STEP/DIR) Hello FPGA Kit wiring, TMC5160 driver modules
    Firmware ↔ gripper servo CorePWM channel 1 in the fabric, APB registers at 0x5000_0000, output on D3 (N7) Gripper servo (MG996R)
    Power 24 V PSU for the TMC5160 modules (VM), DC/DC 24 → 6 V for the servo, kit from USB; one GND star point at the PSU minus Power and servo

    Software reuse boundary¶

    The physical control path is:

    MoveIt 2
  -> ros2_control
  -> ROBOTIS dynamixel_hardware_interface
  -> DynamixelSDK
  -> USB (MCP2221A, /dev/ttyACM0) -> PIC32 -> MMUART_0
  -> SmartFusion2 virtual DYNAMIXEL devices (IDs 1-6 axes, ID 7 gripper)
  -> TMC5160 over SPI -> stepper motors
  -> CorePWM -> gripper servo

    Reuse the existing ROBOTIS hardware interface if source analysis confirms that its model configuration, protocol operations, control-table accesses, command/state interfaces, and timing requirements can be supported. Do not add a project-specific smartfusion2_hardware_interface pre-emptively. Implement only the device behavior needed by the verified host stack, not a presumed complete XM430 clone. Two host requirements come from the kit, not from DYNAMIXEL: the host must send & once after opening the port, and a 0x00 after any packet that ends with 0x25 (see Host link).

    The devices report project model numbers where they differ from a real DYNAMIXEL: the axes report XW430-T333-R (1270), the gripper servo 0x5356, the controller 0x5358. Whether the ROBOTIS stack accepts these must be checked before it is configured (see the compatibility specification).

    Reusing the OpenMANIPULATOR-X ROS application does not make its robot model or joint/controller configuration valid for Moveo. MoveIt planning groups, joint names, limits, kinematics, transmission assumptions, ros2_control interfaces, and controller configuration must agree with a verified Moveo description and the physical stepper setup.

    The Robot PC image is intentionally separate from the Operator PC runtime. MoveIt, RViz2, and Gazebo do not belong in the Robot PC image. In simulation, route ros2_control to the selected Gazebo integration; on the real robot, route it to the DYNAMIXEL/SmartFusion2 path. Keep the robot model and joint semantics consistent across both modes.

    Operating assumptions¶

    • The Robot PC target is Ubuntu 24.04 with ROS 2 Jazzy; the Robot PC profile uses Docker.
    • The Operator PC runs ROS 2 Jazzy and reaches the Robot PC using DDS over the configured network.
    • The kit enumerates through its MCP2221A as a USB CDC ACM device, commonly /dev/ttyACM0. Only the Robot PC owns this connection; the Operator PC does not require direct USB access.
    • DDS domain ID, interface selection, discovery, and firewall policy must be configured consistently across hosts. SSH is for administration, not the ROS data path.
    • Positioning is open loop: no encoders, no limit switches, no homing. The arm is placed in the start pose by hand before power-up; the servo position is unknown until the first command.
    • Power-up order: 24 V (TMC5160 logic runs from VM) and the servo DC/DC before the kit.

    Robot PC¶

    Responsibility¶

    The Robot PC owns the real-time-facing ROS 2 control path and is the only computer that connects directly to the SmartFusion2 USB CDC device:

    ros2_control
  -> ROBOTIS dynamixel_hardware_interface
  -> DynamixelSDK
  -> USB CDC (commonly /dev/ttyACM0)
  -> SmartFusion2
  -> stepper motor control

    The stock ROBOTIS hardware interface is the preferred starting point, but it must not be assumed compatible until the exact protocol and control-table accesses have been checked against current Jazzy source. See the compatibility specification.

    Host and container¶

    The target Robot PC host is Ubuntu 24.04 with Docker Engine and Docker Compose. The paths below (docker/, ros2_ws/, ros2_robot.repos) are in the Robot PC repository, not in this firmware repository. Its current docker/ profile is based on ros:jazzy-ros-base. It imports the DYNAMIXEL SDK/interface dependencies through ros2_robot.repos, builds the project-owned packages, and maps /dev/ttyACM0 into the container with the dialout group.

    MoveIt 2, RViz2, Gazebo, and the Operator PC application are intentionally excluded from this image. The Operator PC owns those dependencies and connects over ROS 2 DDS.

    Build and start the Robot PC container from the Robot PC repository root:

    docker compose -f docker/docker-compose.yml build
docker compose -f docker/docker-compose.yml run --rm smartmanipulator_x

    Before starting, connect the board and confirm the device path on the Linux host. The kit appears through its MCP2221A USB-UART; the host must open it at 460800 bps and send & once before the first DYNAMIXEL packet (see Host link):

    lsusb
ls -l /dev/ttyACM0

    If the board enumerates under another /dev/ttyACM* path, update the Compose device mapping. Ensure the host user and container have appropriate device permissions. Windows does not expose a Linux /dev/ttyACM0 device directly to this container configuration.

    Inside the container, inspect the available packages with:

    ros2 pkg list | grep -E '^(dynamixel_sdk|dynamixel_interfaces|dynamixel_hardware_interface|smartmanipulator_x_)'

    The current launch/configuration packages are scaffolds. No complete physical bringup or SmartFusion2 hardware operation is documented as validated.

    Network and operation¶

    The Robot PC communicates with the Operator PC using ROS 2 DDS over the configured network.     BCN3D Moveo Mechanics¶

    Mechanical source¶

    The target arm mechanics are based on the BCN3D Moveo project, not on the OpenMANIPULATOR-X geometry. The upstream repository provides CAD files, STL files, assembly/user documentation, a bill of materials, and original firmware. Its README describes an educational, additively manufactured arm controlled by Arduino-based electronics.

    This project replaces/adapts the control electronics; it does not claim that the original Moveo firmware or electronics are part of the SmartFusion2 control path. Refer to the upstream repository and its license for the authoritative mechanical files, assembly details, and attribution requirements.

    ROS model integration¶

    The intended home for the project-owned ROS model is:

    ros2_ws/src/smartmanipulator_x/smartmanipulator_x_description/

    That package currently contains only empty placeholders. No Moveo URDF/Xacro, meshes, joint definitions, kinematic parameters, or ROS visualization configuration have been integrated or validated yet.

    When integrating the model:

    • Use BCN3D Moveo geometry and assembly as the mechanical source of truth.
    • Record the source revision and any project-specific changes to CAD/STL-derived geometry.
    • Establish the base frame, link frames, joint axes, zero positions, and units from the source design and assembled robot.
    • Verify joint ranges and collision geometry against the physical arm; do not inherit OpenMANIPULATOR-X limits or joint names.
    • Define and document each Moveo joint-to-stepper mapping, transmission, microstepping, homing/reference method, and position scaling only after the hardware is selected and measured.
    • Keep MoveIt planning groups, ros2_control joints, Gazebo joints, and physical motor mapping consistent.
    • Preserve upstream license and attribution notices for imported or adapted assets. Do not assume that the project repository's license changes third-party asset licensing.

    Acceptance checks¶

    Before a model is treated as the canonical robot description, validate that it parses in URDF/Xacro tooling, has a connected link tree and correct joint types/axes, and produces a useful RViz visualization.
